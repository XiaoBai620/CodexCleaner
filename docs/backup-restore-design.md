## 任务 2、3 的测量安排

真实目录只读。测界面和性能前，在 `%TEMP%` 创建隔离副本：SQLite 使用只读源连接及 backup API，其余普通文件复制，不跟随目录联接；遇到无法一致复制或无法读取的必要文件应报告，不能悄悄省略。副本中的受控绝对路径仅在副本内重定向；验证进程的 `CODEX_HOME` 和事务目录都指向隔离目录，不能解析回真实会话文件。复制不会保留原进程所持有的文件锁，因此锁竞争行为另用合成数据验证，不能把副本锁结果当作真实使用状态。

Snapshot 测量覆盖：数据库结构检查和聊天/自动化查询、会话目录与元数据扫描、聊天锁检测、消息计数、会话文件大小汇总及剩余路径检查。当前代码并未统计消息 JSON 字节数，“大小”来自会话文件；报告按实际执行段命名。使用相同副本与相同输入记录首次运行和随后运行，不能将首次运行冒充清空系统缓存后的冷启动。临时埋点不进入正式产品。

发现某段超过 300ms 后先定位重复查询、重复路径检查、文件读取或解压开销，再做最小优化；没有超阈值瓶颈时只记录测量，不为优化而改代码。引用扫描不能改为只靠文件名，也不能跳过压缩文件或使用中检测。

现有 `ChatView` 的工具项默认折叠，展开时显示引擎提供的全部参数和结果。`PreviewLimit = 20_000` 仅用于普通消息，不能据此宣称工具内容也采用两万字预览。先验证放宽至 200,000 后的实际工具展开性能；确有卡顿时再修对应布局原因。

## 任务 4：选择的方案

采用“按行导出 + 原会话文件”的持久备份包；运行中删除同样必须备份。普通恢复要求 Codex 完全退出，同时仍占用会话整理锁、所选聊天写入锁和清理工具互斥。首版不提供运行中恢复。

持久备份和现有 `Transactions` 分开：`Transactions` 继续承担离线操作失败后的完整回滚；成功清理后移除临时事务目录，保留持久备份。不能只把 `RemoveTransaction` 删掉，否则长期占用整库空间，也无法可靠按聊天恢复。

### 备份格式与空间

路径：`%LOCALAPPDATA%/CodexCleaner/Backups/sessions-<时间戳>-<随机ID>/`，与临时事务目录同级。

- `manifest.json`：格式版本、原数据根目录、创建时间、来源执行模式、聊天摘要、所有已识别数据库的存在状态、结构指纹和迁移记录摘要、行数、内容摘要、文件相对路径/长度/SHA-256、分叉依赖、附加清理范围、阶段状态。
- `rows.sqlite`：独立 SQLite 容器，按源数据库和表分组保存所有将删除的行，以及将修改字段的前值；保留 SQLite 值类型和 NULL，不把值统一转换成字符串。容器使用程序内固定的格式，不执行备份中提供的 SQL。
- `files/<原相对路径>`：原始会话、分段和 `.jsonl.zst` 文件；压缩文件按原字节保存。明确记录原先不存在的文件，不伪造空文件。
- 索引被移除的行与桌面共享历史字段记入清单；队列版本和关联字段前值存入行容器，记录所属聊天或所属全局附加组。离线改写前的桌面文件另外保存作故障核对材料。
- `indexes/<索引路径>.before` / `.after`：运行中改写索引时，在同一索引写入锁内持久保存该次改写的完整前后内容，清单记录两者摘要；不能仅靠所选行判断是否发生半写。
- 操作日志记录每个数据库/文件阶段的预期前后状态；正在生成或中断的包不能作为普通可恢复备份显示。

长期空间为所选数据行、所选文件、清单与容器开销；运行中还保留实际改写索引的完整前后内容，估算按原索引长度的两倍计入这部分，不声称固定压缩比例。离线清理峰值还需现有整库事务副本；恢复前也需要当前数据的事务副本。预览显示估计新增空间，备份完成后显示实际占用；备份写入失败则停止，不继续未验证的数据删除。估算不代替对实际写入失败的处理。

### 备份与恢复范围

必须按已验证的清理动作覆盖以下七个数据库，而不是只处理三个主库：

| 数据库 | 内容 |
|---|---|
| `state_5.sqlite` | `threads`、附件、动态工具、回执、反馈、派生边；额外记录未选子聊天被置空的父引用 |
| `thread_history_1.sqlite` | 消息、轮次、实时条目、投影状态 |
| `memories_1.sqlite` | 所选聊天的提取记忆；全局清理时另存全部受影响记忆与作业 |
| `logs_2.sqlite` | 所选聊天日志；全局清理时另存全部日志 |
| `goals_1.sqlite` | 目标及延续状态 |
| `queue_1.sqlite` | 排队条目与版本；显式处理触发器副作用 |
| `sqlite/codex-dev.db` | 本地目录、扫描条目、时间线、可视化建议、收件箱与自动化运行记录；不恢复或覆盖自动化定义 |

只从程序生成的 `SqlAction` 和已核查的关联关系确定导出范围。不能漏掉 `ClearReference`、触发器修改或把 `CatalogRevision` 当作删除行。

普通聊天恢复包含数据库行、原相对路径的会话文件，以及 `session_index.jsonl` / `history.jsonl` 中该聊天被删除的行。索引增量合并，保留现有无关行；重复历史行按原条目重数处理，不把合法重复输入全部去重。相同会话 ID 的索引内容冲突时拒绝该次恢复预览。

正常恢复不回写整份 `.codex-global-state.json` 或其 `.bak`，不复原置顶、草稿、窗口/标签等桌面状态；离线删除时的这些差异保留作故障回滚材料，界面在恢复前明确说明。运行中删除本来就不修改桌面状态。

“全部记忆”“共享历史与日志”的内容单列为附加清理备份组，按组恢复，不能随意归入某一个聊天。恢复该组需单独勾选；涉及桌面共享 `prompt-history` 时仅恢复已识别且仍符合删除后状态的字段，保留其他状态。任一目标发生冲突即拒绝整组，不覆盖后来生成的内容。失效引用修复沿用现有事务回滚，不制造不存在的可恢复聊天。

“仅清理记录”的聊天只恢复其数据库和索引记录；不访问、不备份、不恢复异常会话路径。项目、工作树、插件、配置、凭证不进入备份。

### 运行中删除与备份一致性

1. 按现有顺序取得清理工具互斥、整理锁、所选聊天写入锁，复查结构、自动化、分叉关系、时间戳和文件指纹。
2. 准备完整备份包，逐库导出所影响的数据行，保存关联前值和原文件。索引内容在对应文件锁下读取。核对类型化行内容摘要、行数、文件摘要和备份数据库完整性，落盘后标为可用于恢复，才允许开始删除。
3. 保持逐库事务：每个 `BEGIN IMMEDIATE` 内重新读取完整受影响行集，与已落盘备份比对；不一致就停止，不遗漏新出现的行，也不更新备份来掩盖先前已提交的部分。
4. 索引改写时在同一文件锁内比对待移除条目与备份，先持久保存完整前后内容及摘要，再移除对应行并落盘校验；不回写准备阶段读到的旧整份索引。可捕获写入异常在该锁内还原原内容并验证，还原失败则保留完整材料。会话文件仍由聊天锁、整理锁和指纹保护。
5. 继续最后处理 `state_5.sqlite`；每步记录完成状态，全部校验通过后将包标记为正常可恢复的已完成备份。

这不是跨数据库的原子快照，也不会长期同时持有七个库的写锁。保证的是每次实际删除/修改的内容都已持久保存，并在对应写入锁内验证一致；各库间出现不一致时停止并进入故障处理。

### 结构兼容、冲突与依赖

- 备份格式必须受支持，原数据根目录必须匹配。首版不是跨机器或跨目录迁移工具。
- 对所有已识别数据库记录并核对存在状态、现有 `Db.SchemaHash` 指纹及迁移记录摘要，且当前结构仍须匹配 `Catalog.Schemas`。迁移摘要包含版本/状态/校验值或 ID/前驱/校验值。出现未知版本库、结构改变、迁移记录变化或必需数据库缺失时拒绝恢复，不猜测迁移，不自动创建替代数据库。
- 普通恢复按聊天 ID 跳过当前已存在的聊天，界面禁用这些复选框并显示原因；“全选”只选可恢复项。跳过该聊天的所有从属内容，而不是只跳过 `threads` 行。
- 被删父引用仅在存活子聊天仍符合记录的删除后状态时恢复；否则在预览中报告冲突，不覆盖新的父引用。关联边端点必须存在或同批恢复。
- 项目或分组等外部引用也须存在；例如原 `project_id` 或 `thread_section_id` 对应对象已被删除，则明确报告并拒绝相关恢复，不自动重建对象或置空字段。
- `history_base.thread_id` 指向的父聊天不在备份中时明确列出：父聊天当前存在且文件可用才允许恢复；父聊天同在备份时要求先恢复或同批选择。找不到完整父链则阻止相关聊天恢复，不生成断裂历史。
- 恢复前检查主键、唯一键、外键和目标文件冲突。除“聊天已经存在”按上述规则跳过外，其他冲突拒绝本次选择，不用 `INSERT OR REPLACE` 或任意忽略错误。
- `local_thread_catalog_metadata.catalog_revision` 按恢复动作递增，不倒退到备份值。队列版本是全库单调变更标记；恢复队列项后为受影响聊天生成新版本，不回退到备份时的旧版本，也不覆盖无关聊天的版本。聊天 INSERT 触发器改写的时间派生列须还原备份值；这些行为单独测试。

### 恢复与失败回滚

普通恢复先做只读预览，列出可恢复/跳过/冲突聊天、依赖、文件数量、大小和附加清理组。确认执行时重新核对全部条件。

Codex 必须退出；获取互斥、整理锁和聊天写入锁后复查进程。先备份此次会修改的当前数据库及文件，记录哪些目标原先不存在；全部备份与条件验证通过后再写入。关系按正确顺序恢复，保留非目标数据，文件通过临时文件和原子替换落到原相对路径。提交后核对行内容、数量、索引、文件摘要、SQLite 一致性及相关外键。

遇到可捕获失败时回滚未提交事务，使用本次恢复的事务副本还原已提交部分，删除本次新建且原先不存在的文件；还原验证失败时保留材料、阻止后续写入并明确标识故障路径。持久备份不因一次恢复完成而自动删除。

运行中删除失败时，当前库按原有事务回滚，已提交库不能用整库副本覆盖，因为 Codex 仍会写其他聊天。首版保留完整备份和操作日志，标为“部分执行，需退出 Codex 处理”，不宣称已自动完整回滚。

故障处理有独立入口：日常恢复的“当前已存在则跳过”不能处理主记录仍在但部分从属数据已删除的状态。用户退出 Codex 后，故障预览要求每库受影响行集为完整清理前状态或全部删除后的状态，文件符合已记录的前后状态，只补回已确认缺失的内容。索引有完整日志时，仅接受完整前态/后态或其后追加的无关有效 JSON 行；不符合这些状态、无效 UTF-8 或无法判定的半写拒绝自动覆盖并保留材料。故障处理本身也建立事务副本并验证，不能只因为主聊天还在列表中就将半删除备份视为无需恢复。

多库和文件之间仍无断电原子性。提交与记日志之间的中断必须在故障恢复时对照前后内容判断，不能仅凭某个“完成”标记推断数据未变。启动 `Snapshot` 只调用 `BackupRecoveryIssues` 做轻量清单检查，不逐份散列行容器和会话文件；完整摘要校验留在读取和实际使用备份时。无法确定时阻止继续写入并保留可诊断材料，不自动猜测。

### 路径和备份管理界面

- 备份根目录与数据目录、事务目录互不包含。所有源、目标和备份路径复用 `SafePaths` 与独立普通文件检查，拒绝绝对路径、`..`、设备路径、数据流、目录联接、符号链接和硬链接。
- 清单中的路径和数据库行都是不可信输入；核对格式、长度、摘要、白名单及数据根目录，在写入和删除前再次验证。文件存在但与预期不同即报冲突。
- 主界面使用 `ThemeButton` 增加“备份与恢复”；配色只取 `DesktopTheme`。备份窗口显示日期、聊天数量、来源模式、实际占用及正常/中断状态，支持按聊天选择、全选可恢复项、单独选择附加组。
- 读取、预览、恢复、删除旧备份均在后台执行，并报告阶段与累计耗时。删除旧备份要显示其日期、数量及实际大小后确认；有未处理故障的备份不能作为普通旧备份删除。没有自动过期删除策略。

### 验收测试

合成数据覆盖：七库相关行、分段/压缩会话、索引、父子关联和附加组的备份恢复；已有聊天整组跳过；结构/存在状态不一致和损坏备份拒绝；路径穿越、链接和文件冲突；运行中写入锁/整理锁竞争及锁释放；备份失败发生在删除前；每个提交与文件阶段故障后的可恢复性；半删除状态的故障恢复；触发器与目录版本；未选聊天、项目、自动化和桌面新状态保持；后台操作的界面响应。

“完整恢复”指上述承诺的数据范围，桌面置顶/草稿/窗口状态不属于普通聊天恢复范围。测试不得用真实库执行删除或恢复。
